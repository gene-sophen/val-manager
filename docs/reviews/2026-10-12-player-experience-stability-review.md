# v0.5 玩家体验完成情况复核与下一轮建议

复核日期：2026-10-12。代码基线：`bf95362`（Release v0.5）。

本轮结论：上一轮多数界面建议已有实现，但不能将“玩家体验已完成”等同于“旧档、继续比赛、异常恢复已验收”。本轮复现了两个实际缺陷，并验证了一条可能导致明显卡顿的同步执行路径。尚未修改游戏业务代码。

用户反馈：前几个版本开始的比赛，在 6:6 时点继续无反应；出征页缺少返回或底部 Tab。没有取得用户那份存档，因此下述复现不能直接认定为同一个故障。

## 二、优先处理的问题

### S1 / P1：保存事务中止后，恢复备份误报多窗口冲突【已复现】

玩家影响：保存失败后，玩家按系统建议恢复备份，却再次失败；界面把原因说成其他窗口修改，容易让人误以为存档已经损坏或被覆盖。

独立真实 IndexedDB 测试步骤：载入初始档并导出备份 → 修改教练名并保存 → 在写入成功事件触发时中止整个事务 → 再恢复刚导出的备份。

结果：磁盘存档完整回滚，仍为 revision 0；内存 revision 已变成 1。恢复报“其他窗口已更新存档，请重新载入后导入”。重新 load 后恢复成功。这是故障注入测试，模拟事务中止，并非声称用户设备发生了同一存储故障。

原因：[career-store.js](D:/my_program/val-manager/游戏/career-store.js:63) 在事务提交前更新 `revision/observed`；中止后这两个值没有回滚。`restore/restart` 也采用类似的提前更新方式，应一起处理。

改进：只在事务 `oncomplete` 后发布新的内存版本；中止保持原版本。恢复必须兼顾真正的多窗口冲突保护，不能简单去掉冲突检查。提示区分“写入失败”和“其他窗口更新”。默认展示最近成功保存的时间和回合，提供导出未提交进度与重新载入入口。

验收：人为中止保存、导入及重开事务，原档不变、内存版本不前移；故障解除后可恢复；真正的另一窗口写入依然被拦截。

证据：`.artifacts/validation/2026-10-12-stability-recheck/transaction-abort-result.json`。

### S2 / P1：已看完的回放拖回开头后，自动推进一直等待【已复现】

操作：进入第 13 分手枪局 → 关闭自动推进 → 将回放时间轴拖到结束 → 再拖回 0 秒 → 开启自动推进。

结果：界面显示“自动推进已开启”，回放按钮却显示“回放本分”，时间轴持续停在 0 / 67.75 秒，回合也不前进。人工点击“下一分”能进入第 14 分，因此此例属于推进逻辑停滞，整个浏览器并未锁死。

原因：[spatial-view.js](D:/my_program/val-manager/设计文档/UI原型/complete-prototype-01/spatial-view.js:96) 用“已观看”状态决定是否启动回放；同文件第 102 行却仅按时间轴是否到结尾判定仍需等待。[app.js](D:/my_program/val-manager/设计文档/UI原型/complete-prototype-01/app.js:112) 于是每 250ms 继续等待，没有退出条件。

改进：明确区分“本分结果已确认”“当前正在回看”“比赛请求继续”。自动推进开启时，已确认的回放应直接结束或明确恢复播放。不能同时显示“正在自动推进”与静止等待且没有原因。

验收：回放结束、倒拖、暂停、倍速、切后台再返回、减弱动画等组合中，自动推进要么前进，要么明确显示等待条件与解除操作。

证据：`replay-stall-dom.txt`、`replay-stall.jpg`。这是另一条已复现路径，尚不能认定它就是用户 6:6 的原因。

### S3 / P1：缺少回放缓存时，渲染会同步重算历史回合【执行路径与耗时已验证】

[spatial-view.js](D:/my_program/val-manager/设计文档/UI原型/complete-prototype-01/spatial-view.js:86) 在生成视图时直接调用 `S.replay(m)`；[spatial-match.js](D:/my_program/val-manager/游戏/spatial-match.js:122) 在缓存不存在时调用 session，逐回合重建整场历史。这条路径没有进入负责下一分计算的 Worker。

在仓库旧档派生的第 12 分副本上人工删除回放缓存，Node 同步调用耗时 **14,228ms**，得到 336 个事件。该数字是本机模型测试耗时，不是手机实测；也没有证明用户旧档缺少缓存。正常第 12 分摘要不一定调用回放，关键分或主动回看才更相关。

改进：回放重建也放进 Worker；先呈现比分、返回与加载状态，再异步填充沙盘。恢复进度显示已重建回合数和耗时，允许停止回放并看战报。只有账本验证通过才能继续比赛；校验失败时保留原档，不应重掷历史赛果。

此外，Worker 冷启动也会从开局重建历史；现有超时为 60 秒。应显示“正在恢复旧比赛 · 已核对 X/Y 分”，并区分恢复历史与计算新的一分，避免整段等待都叫“正在推演本分”。

### S4 / P1：征战页导航消失仍未关闭【用户反馈，正常样本未复现】

本轮实际页面为 v0.5，在有效视口 390×844 下，征战根页有战队、征战、档案三个按钮；比赛页有左上返回和“保存并返回征战”。从第 14 分返回并刷新后，回合与暂停状态保留。没有复现正常页面同时缺少返回与 Tab。

值得补强的代码路径：初始 HTML 的返回按钮隐藏、底部 nav 为空；[app.js](D:/my_program/val-manager/设计文档/UI原型/complete-prototype-01/app.js:14) 先等待存档，后续 `R.init/D.sync` 不在存档捕获范围；渲染视图也早于导航填充。若恢复卡住、脚本加载失败或视图抛错，导航外壳可能无法建立。这是机制风险，不是对用户现场原因的定论。

改进：主导航与恢复入口先静态呈现；启动、迁移及页面渲染失败有统一错误页。征战根页可不设“返回上一页”，但必须保留主导航；流程页必须提供明确的返回目的地；加载、计算、错误页始终能回到可操作的恢复界面。

验收应包含：旧版本升级、PWA 冷启动、资源失败、存档读取等待、恢复抛错、键盘弹起、横屏及安全区。不能仅检查按钮存在于 DOM，还要检查可见且可点击。

- 浏览器复现 S2，并验证手动“下一分”可解除这条停滞；S3为移除缓存副本的同步模型测试。
- 导航截图的有效尺寸为390×844。后续请求的320×568及844×390覆盖没有在即时读数中生效，**不计为完成的窄屏/横屏验证**；原始读数保留在证据目录。
