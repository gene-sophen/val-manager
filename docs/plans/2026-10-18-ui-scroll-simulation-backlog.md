待办：

- [ ] 以用户反馈过的 vivo 桌面图标、竖屏为主要复现入口；记录当时版本，另测相同站点的浏览器入口，不能直接推断桌面图标使用的内核。

- [ ] 分别从文字、卡片、卡图、按钮附近及沙盘上开始竖向滑动，记录实际命中的元素、滚动偏移变化和到达末尾的能力。
- [ ] 检查父链高度、flex收缩、`min-height:0`、`overflow`、定位、`touch-action`、触摸监听是否取消默认行为，以及透明覆盖层/遗留模态是否截获输入。
- [ ] 检查弹窗打开、关闭、Esc、系统返回及切页后，滚动锁是否正确释放；不能因隐藏的弹窗残留而让正文长期无法触摸滚动。
- [ ] 区分“没有形成滚动区”“手势被拦截”“滚动后立即被刷新拉回”“已到边界”。四者修法不同，不统一归因为屏幕比例。
- [ ] 检查逐分刷新、过滤、展开详情、图片加载和焦点更新是否反复重置位置；玩家正在阅读战报时不自动拉回顶部。
- [ ] 沙盘若支持拖动，只在明确交互区域处理拖动；普通页面滑动仍可通过周边正文进入，不给全页设置 `touch-action:none`。
- [ ] 确认最后一项能滚到导航/动作区上方，且可以点击；固定栏、安全区和键盘不覆盖它。
- [ ] 保留允许用户缩放的设置，不用全页缩小来掩盖缺失滚动。

当前根节点和外壳使用 `overflow:hidden`，正文使用 `overflow:auto`；这是一种可能成立的应用布局。**不能仅凭根节点禁滚就判定原因，也不能把根节点全部改成auto导致双滚动。** 应先查清目标容器及手势路径。

验收证据必须包含：触摸向上、向下后真实 `scrollTop` 的变化；末尾内容与按钮可见可点；关闭模态后恢复正文滑动。脚本赋值 `scrollTop`、滚轮、键盘滚动分别记录，不能合并成手机触摸通过。

### U06：UI关闭条件

1. 所有有长内容的页面与弹窗能通过实际触摸上下到达末尾；无内容时不强求产生滚动。
2. 自动推进、切页、弹窗关闭和后台返回后仍可滚动，已读位置合理保留。
3. 普通/大字、窄屏/横屏、系统字体放大、键盘及安全区均覆盖；模拟测试先确认有效视口，再判定结果。
4. vivo桌面启动与同机浏览器结果分别报告。原反馈设备作为必测对象；其他设备信息由实际诊断确认。
5. 可用性、对比度、焦点、空态/加载/错误与主要玩家旅程通过。没有真机证据时保留“真机待验收”。

## 五、引擎目标：提前建能力模型，按真实赛程模拟

### 5.1 模型组成

用户要求的核心保持为：**五位选手三维 + 队伍地图战力 + 队伍三维**。教练、战术及特工作为现有规则中的条件修正，与基础战力分开解释。

| 层 | 输入 | 预建模输出 | 更新时机 |
| --- | --- | --- | --- |
| 选手 | 五名唯一选手的AIM/SYN/SEN、身份/卡版本 | 保留五人原值，计算三维汇总及候选分工特征 | 阵容、卡值或模型版本变化 |
| 队伍 | 羁绊、状态、熟练 | 队伍修正向量；状态与稳定能力分开 | 合法成长、换人及状态变化 |
| 地图 | 每图熟练/能力、地图规则、攻守倾向 | 逐图、必要时逐攻守的能力档案 | 图池、地图规则、熟练变化 |
| 条件 | 教练、战术倾向、特工搭配及规则允许的情境 | 本场/本图修正 | 在比赛开始或合法调整边界冻结 |
| 结果随机性 | 比赛、地图、回合种子 | 围绕能力的波动 | 每场独立，不能用浏览次数重抽 |

当前算法以 `0.42*AIM + 0.30*SYN + 0.28*SEN` 等构造数值强度。这是现有实现，并不意味着新模型已认可这些权重。新参数需做敏感性、比分分布和与详细引擎的一致性验证后确定。

**建议结构：**

```text
作者卡库 + 正式五人名单 + 数据来源
                   ↓ 校验 / 缺失策略
版本化 TeamProfile（五人及队伍基础）
                   ↓ 预计算
MapPowerProfile[team][map][side]
                   + 本场状态/战术/特工快照
                   ↓
抽签与赛程 → 可执行比赛节点 → 单图模拟 → BO系列赛
                                  ↓
                         唯一结果账本 / 成长 / 积分
                                  ↓
                         后续对阵、晋级、赛年结果
```

概念关系：`单图攻守能力 = 选手能力贡献 + 队伍贡献 + 地图贡献 + 合法条件修正`；由双方能力差与已校准噪声产生逐分/逐图结果。该式是模块分解，**不是直接相加0–100原值的最终公式**。

## 六、架构决策草案

### ADR-01：预计算能力，而不是固定整季赛果

**建议：** 开局建立全队基础画像；在阶段或比赛的合法边界组合动态快照，再逐场模拟。纯能力计算可缓存；已提交结果由账本保存。

**原因与代价：** 既节省重复计算，又能接住玩家结果改变签表及成长带来的影响；需要维护修订号和缓存失效。整季开局预生成会与后续分支冲突，因此不采用。

### ADR-02：分精度引擎，共用能力含义

**建议：** 玩家对战用现有详细引擎，NPC对战用经过校准的数值/快速引擎；统一输入和语义，不强制所有后台比赛运行空间回放。

**代价：** 需做跨引擎统计一致性验证；不能把只在快速引擎上平衡的参数直接宣称对详细引擎同样成立。

### ADR-03：逻辑赛程顺序与计算速度分开

**建议：** 每场输入在确定的逻辑时点冻结，结果和成长按固定顺序提交；Worker可批量计算确定独立的任务，但不改变逻辑顺序。

**代价：** 需要节点状态和提交协议；换来中断、并发、重试后仍能复现。不能用页面打开次序决定队伍成长顺序。

这些是供后续实施采用的设计草案；权重、波动幅度与预算仍需校准数据，不作为已验证结论。
