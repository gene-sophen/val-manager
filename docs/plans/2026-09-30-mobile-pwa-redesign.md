# 手机端 PWA 前端重做计划

日期：2026-09-30。状态：初稿归档，执行顺序已调整。

> 用户最新要求：玩法将重做，当前先做基础艺术方向与界面，最后才接入引擎。当前执行依据为 [视觉基础阶段计划](2026-09-30-visual-foundation.md)。本文件中四场征程、旧状态映射、固定导航和引擎接入方案仅保留为先前分析，不构成当前设计约束。第一轮 HTML 视觉样稿已完成，见新版计划。

目标：围绕手机竖屏、单手操作和碎片时间游玩，重建布局、视觉系统、组件和交互，形成能连接现有玩法的 PWA。

已确认的审美方向：**“底色偏理性数据感，但要保留人文温度。”** 用稳定的信息结构、清晰的数据比较体现理性，用选手影像、成长经历和克制的叙事体现温度。“底色”先理解为整体气质，不等同于指定深色背景。具体深浅与配色通过对比稿确定。现有卡面与抽卡特效可复用、适配和优化。

## 1. 已检查的现状

本次检查包括 v2 源码、仓库已有大厅/阵容/比赛/开包截图、v16 卡面预览、玩法规则、可玩入口与存档代码。截图是仓库历史产物；本次未运行浏览器或做真机测试，下列运行风险不视为已经实测的故障。

| 现状与依据 | 对重做的影响 |
| --- | --- |
| `设计文档/UI原型/v2/` 是视觉演示；`游戏/play.template.html` 是另一套可玩界面 | 新界面必须接入同一玩法状态，避免维护两套相互偏离的产品 |
| v2 `.phone` 固定为 390×844；页面在模拟手机壳内滚动 | 改为真实视口布局，390 仅作设计基准，不作为运行尺寸 |
| 大厅首屏队标占据较多空间，下一步操作偏靠下 | 首页围绕“当前进度、当前队伍、下一步行动”重排 |
| 阵容使用多边形头像、关系线、细小属性并排 | 展示与编辑分开；提高阵容比较、角色分配的可读性 |
| 顶部常驻教练三维，主要为 9.5px 字；大量厚阴影和立体按钮 | 顶栏减负，重建字体层级与材质层级 |
| 开包结果把完整卡面缩成约 66px 宽 | 完整卡面用于鉴赏；小尺寸使用专门的信息布局 |
| 原型有 BO3/BO5、冠军赛和五张演示开包；可玩版为十张初始包、四场 BO1 切片 | 首版按可玩闭环设计，未来长赛季单独扩展 |
| v16 卡面、人物半身像、队标、特工头像、品质底纹、钻卡海报、字体均已有资源 | 将精力投向界面容器、构图和交互，优先复用素材 |
| `v2/css/tokens.css` 的素材相对路径按 CSS 所在目录解析后指向不存在的 `设计文档/素材库/` | 新版统一素材映射和资源路径，并验证字体与图片实际加载 |
| 检索未发现 Web App Manifest 或 Service Worker；唯一 manifest 为引擎场景数据 | PWA 能力需要专项实现，不能把响应式页面直接视作完成 |

已有卡面预览只作为视觉参考，属性、品质与抽卡结果从当前 catalog 和玩法状态读取，避免复制旧截图数值。

## 2. 重做边界与设计原则

### 重建

- 页面层级、导航、首屏构图、阵容编辑、比赛信息排列。
- 颜色语义、字体、间距、按钮、标签、弹层、空状态与反馈。
- 手机触控、系统返回、视口变化、PWA 安装与缓存更新体验。

### 复用并适配

- 选手卡 v16 的长六边形轮廓、品质识别、人物和钻卡海报。
- 已有开包与逐张翻转的表现语言，保留手动节奏并加入明确跳过入口。
- `游戏/` 的规则、命令、状态、成长、存档，以及 `引擎/` 比赛能力。

### 原则

1. 每个操作页面有一个明确的主要行动，行动文案随真实状态变化。
2. 界面装饰服务于选手与比赛；金属纹理、高光和稀有色主要留给卡面与奖励。
3. 展示、比较、编辑使用不同信息密度，不靠整体缩放适配所有场景。
4. 本轮库存与永久图鉴始终明确区分，图鉴里的卡不能误显示为可上场。
5. 只展示已有依据的数值与效果；原型中的模拟默契、战力、教练属性不直接接入产品。
6. 首版闭环围绕现有四场测试征程；完整赛年、联网、薪资合同另立项目。
7. 人物姓名与形象优先于编号和评分；展示数据变化时说明来自哪次成长或哪场表现。温度来自真实经历，不靠额外暖色装饰或无依据的情绪标签。

## 3. 信息架构与主流程

建议底部四个一级入口：**征程 / 战队 / 收藏 / 生涯**。

| 入口 | 主要内容 | 设计约束 |
| --- | --- | --- |
| 征程 | 当前赛程、对手、待办、继续征程 | 首页只突出当前节点，完整赛程展开查看 |
| 战队 | 五人名单、本轮候选、特工、IGL、职责、成长 | 五人紧凑总览 + 可读列表；换人通过点击完成 |
| 收藏 | 永久图鉴、品质与赛区筛选、卡面鉴赏 | 标注本轮是否持有；不承担直接选人功能 |
| 生涯 | 历史战绩、定格阵容、荣誉、设置 | 设置放在这里，不再使用含糊的“更多”容纳核心功能 |

卡包是征程中的行动，可从征程待办和战队补强进入。比赛、开包演出和结算使用专注页面，暂时收起一级导航，并提供明确返回或继续入口。

主流程：

```text
首次进入 / 恢复征程
  → 选择赛区并开十张初始包
  → 逐张揭示或跳过 → 结果总览
  → 选出五人 → 配置特工 / IGL / 职责
  → 赛前备战 → 比赛 → 赛后复盘
  → 第1～3场后普通成长
      第2场后另含阶段成长与可用补强
  → 下一场
  → 第4场后征程结算 → 生涯归档 → 新征程
```

页面跳转由真实状态决定：待揭示卡包、未完成阵容、待选成长、进行中的比赛各有自己的恢复入口。选人不足、同名重复、超过钻卡上限等情况，在对应操作处解释原因。

## 4. 关键页面怎么重做

| 页面 | 建议结构 | 验收重点 |
| --- | --- | --- |
| 征程首页 | 简洁身份栏 → 当前对阵主视觉 → 进度与战绩 → 队伍摘要 → 待办 | 390×844 首屏能看到下一步；小屏仍有可触及主行动 |
| 初始选人与战队 | 五个可点击位置 → 本轮候选列表 → 筛选 → 底部已选数量与确认 | 不要求拖动；编辑特工、IGL、职责时能看到当前对象 |
| 选手详情 | 大卡面 → 卡牌基础属性 → 本轮成长与状态 → 相关操作 | 基础值与临时加成分区；钻卡与普通卡均正常显示 |
| 开包 | 包面与赛区 → 单卡揭示 → 进度 → 十张结果列表/两列网格 | 避免五张完整卡挤一行；跳过和中断不改变结果 |
| 赛前备战 | 对手与地图 → 阵容核对 → 训练/侦察/恢复 → 开赛 | 明确每场次数与效果；已用备战不再次承诺生效 |
| 比赛 | 紧凑比分与回合 → 地图 → 关键事件 → 回合间操作 | 分数和关键行动保持可见，长日志单独展开 |
| 战术调整 | 当前计划 → 可选方案及影响 → 确认 | 显示可操作窗口、暂停余量和已生效状态 |
| 赛后复盘/成长 | 胜负和比分 → 关键表现 → 三选一成长 → 继续 | 能区分比赛结果与下一步决策；不重复发奖励 |
| 收藏/生涯 | 筛选图鉴 / 征程记录列表 → 详情 | 长列表按需加载，未持有与本轮持有明确区分 |

比赛竖屏以可读地图和简短事件为核心；放大地图进入独立视图，横屏作为增强，不要求用户旋转才能完成比赛。当前地图能力边界保持真实，UI 不假装已有完整二维比赛。

选手详情允许从底部面板进入，长内容可展开为完整页面；筛选使用短面板，完整阵容编辑使用页面，避免多层弹窗套叠。

## 5. 视觉方向：先对比，再定稿

第一轮制作两组同内容、同尺寸的高保真方案，每组覆盖“征程首页 + 战队 + 选手详情”。用同一批真实素材，确保比较的是设计。

- **A：暖石墨，优先探索。** 中性偏暖的深色表面、米白正文、低饱和灰绿强调；规整的数据分栏与宽松行距，人物保留自然肤色。卡面保留金银铜钻的材质，外围控件降低光泽。
- **B：暖灰白。** 米灰背景、炭黑正文、深灰绿强调；以档案和体育编辑排版组织信息，完整卡面作为对比鲜明的视觉重心。比赛专注视图可采用统一的深色主题，但需验证切换连贯性。

两套方案都遵循同一个方向，不再比较“冷硬电竞”与“华丽抽卡”。理性主要体现在对齐、比较、层级和准确反馈；温度主要体现在真实人物、成长过程、自然影像和语言。

人文表达的具体落点：

- 首页用队伍合照式人物构图或一位代表选手配合五人摘要，不让巨型总评分取代队伍身份。
- 阵容先呈现姓名、特工和职责，再展示数值；用明确的文字说明配合关系。
- 赛后用真实事件生成一句摘要，例如“第18回合守住关键点位”，并能进入对应回合；不编造人物情绪和故事。
- 生涯保存这一轮的阵容、比分和成长轨迹，让玩家看到队伍经历，而不只是累计次数。
- 文案短而自然，例如“确认这套阵容”“继续征程”；解释错误时说明可调整的地方。

用真实手机尺寸判断：是否一眼知道下一步、文字能否直接阅读、卡面是否成为视觉焦点、连续使用是否疲劳。没有确定方向前，不批量制作其他页面。

### A 方向候选令牌

| 用途 | 候选值 | 规则 |
| --- | --- | --- |
| 页面背景 | `#121718` | 中性石墨，避免大面积花纹 |
| 内容表面 / 浮层 | `#1B2325` / `#273235` | 主要靠明度区分层级 |
| 边线 | `#3A484B` | 辅助分组，不给每块内容加厚边框 |
| 主文字 / 次文字 | `#F3EEE5` / `#ADB9B8` | 米白减轻冷感，次文字仍承担可阅读内容 |
| 主要行动 | `#9CC8BF` | 低饱和灰绿，搭配深色文字；最终组合测对比度 |
| 信息 / 成功 / 警告 | `#80C9EB` / `#8CD3A7` / `#E7BE73` | 使用文字和图标辅助，不只依赖颜色 |
| 品质色 | 复用铜银金钻体系 | 品质色与功能状态色分工；比赛攻防色限于比赛语境 |

B 方向先用背景 `#F3F0E8`、表面 `#FFFCF5`、主文字 `#202A2A`、强调 `#285E59` 制作对比。两套均避免用强橙色滤镜处理人物来制造温暖感。

字体候选：

1. 系统中文无衬线 + Rajdhani 数字，Anton 仅用于少量大比分和选手 ID（推荐）。
2. 系统中文无衬线 + 系统数字，偏清晰克制。
3. 系统中文正文 + 得意黑少量标题 + Rajdhani 数字，偏游戏感；需验证字体加载成本。

统一规格：

- 页面标题 24/28px，模块标题 18/24px，正文与按钮 16/24px，辅助信息 13/18px；关键内容不使用 9～11px 小字。
- 数字强调 28～40px；比分采用等宽数字特性，变化时不跳动。
- 间距尺度：4、8、12、16、24、32px；手机左右边距默认 16px。
- 表面圆角 12px、面板 16～20px、按钮 10px；斜切只作为少量品牌细节，长六边形主要归属卡面。
- 主按钮高 48～52px，交互目标至少 44×44px；图标本体 20～24px。
- 触控反馈约 100～160ms，面板切换约 180～240ms；常规页面不持续呼吸或闪光。
- 正文对比度以 4.5:1 为验收目标，交互边界与焦点可见性单独检查；所有候选颜色需组合实测。

## 6. 组件与素材策略

### 首批组件

`AppShell`、`TopBar`、`BottomNav`、`PrimaryButton`、`IconButton`、`SegmentedControl`、`StatusBadge`、`MatchSummary`、`LineupSlot`、`PlayerRow`、`PlayerCard`、`PlayerDetail`、`BottomSheet`、`ConfirmDialog`、`Toast`、`EmptyState`、`LoadingState`、`ErrorState`。

按钮具备默认、按下、禁用、提交中、键盘焦点状态；可选项具有未选、选中、不可选及原因。弹层管理焦点、返回和关闭后焦点恢复，滚动不会穿透到底页。错误提示就地展示，不能只靠短暂 Toast。

### 同一选手，三种展示

- **完整卡面**：详情与抽卡揭示，保持 300:470 原始比例；屏幕允许时使用约 240～300px 宽。非常矮的屏幕允许滚动。
- **收藏缩略图**：两列展示卡面外观，姓名、品质和关键数值放在卡外可读位置；点击看完整详情。
- **管理列表**：头像、姓名、品质、角色、必要数值、状态；不把卡面内所有细节缩进一行。

素材优化保留原件，另生成按用途分尺寸的派生资源；人物裁切逐个检查头顶与面部，钻卡单独校验。统一 asset map，缺图有占位。首屏只预载必需人物、队标和字体，图鉴按需加载。

抽卡沿用现有翻牌与品质演出，补全卡背和包面；铜银不过度占时，金钻保留强调。手动点击翻开、再次点击继续的节奏以 v2.4 修订说明为基准，先消除旧文档中“自动流转”等冲突。减动效模式使用淡入，关闭震屏和强闪光；跳过直接进入已保存结果。

## 7. PWA 专项要求

| 项目 | 实现与验收要求 |
| --- | --- |
| 手机布局 | 使用动态视口并设回退；适配顶部/底部 safe area；软键盘弹出后输入项和确认按钮可达 |
| 返回行为 | 先关闭当前弹层，再返回上级；恢复上级滚动位置；进行中的比赛保留有效检查点 |
| 安装 | 补 manifest、图标、主题色与 standalone；Android 与 iOS 按各自能力显示安装引导 |
| 服务方式 | 正式使用 HTTPS；本机调试用 localhost；不将 file:// 可打开等同于 PWA 可用 |
| 离线边界 | 已缓存应用与当前征程所需规则可继续使用；未缓存卡图显示占位；完整素材离线包后置 |
| 存档 | 复用 IndexedDB 与现有命令校验；资源缓存和存档分开管理；保存失败不展示成功 |
| 中断恢复 | 开包、回合间、成长选择等持久化检查点可恢复；不承诺后台持续模拟或任意 tick 恢复 |
| 版本更新 | 新资源准备完整后提示更新，在安全节点切换；比赛/抽卡提交中不强制刷新；不清空生涯数据 |
| 兼容性 | iOS Safari 与主屏 Web App、Android Chrome 浏览器与安装模式分别验证 |
| 存档迁移 | 当前本地入口与未来 HTTPS 入口可能不共享存储，先准备导出/校验导入流程；不默认自动继承 |

安装能力随系统和浏览器不同，具体引导在目标真机上验收。参考 [web.dev 安装说明](https://web.dev/learn/pwa/installation)。安全区参考 [MDN env()](https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Values/env)；缓存与更新方案参考 [Service Worker](https://web.dev/learn/pwa/service-workers) 和 [更新生命周期](https://web.dev/learn/pwa/update)。

## 8. 实施顺序与每阶段交付物

| 阶段 | 工作 | 交付物与完成标准 |
| --- | --- | --- |
| P0 流程与素材盘点 | 核对页面与真实状态、素材映射、规则差异 | 页面清单、状态表、素材清单；每个主要行动可映射到已有命令或明确待开发能力 |
| P1 视觉探索 | 两套风格，各做三张关键页面 | 同尺寸对比稿；在具体画面上确定排版、材质、配色与人物构图 |
| P2 设计系统 | 固定令牌、公共组件、三种卡牌展示 | 可浏览组件样板页，覆盖普通/长文本/禁用/加载/错误/缺图等状态 |
| P3 手机交互原型 | 串起开包、选人、备战、比赛、成长、结算 | 360/390/430px 可交互原型；返回、弹层和键盘流程通顺；演示数据明确标识 |
| P4 真实玩法接入 | 用已有规则、命令和存档替换演示状态 | 四场闭环可走通，刷新不重抽、不重复成长和领奖；图鉴与库存一致 |
| P5 PWA 与真机打磨 | 安装、缓存、更新、中断恢复、性能、可访问性 | 浏览器/安装模式验收记录；发布候选版本及剩余问题清单 |

P1 是最重要的审美检查点，先完成可比较页面，再决定后续统一风格。工期在 P1 定稿、目标设备和接入复杂度确认后估算，不把视觉迭代压缩成一次交付。

## 10. 验收清单

### 视觉与使用

- 360×780、390×844、430×932 及一个矮屏尺寸均能操作；页面无意外横向滚动。
- 首页能快速识别当前赛程、队伍和下一步；主要操作不藏在长地图下面。
- 小卡无需缩放就能读出姓名、品质及必要状态；长选手名、钻卡和缺图均有处理。
- 图标风格统一；普通界面不过度使用发光、描边、材质和斜体。数据清晰但不堆叠仪表盘，人物及其经历有稳定的位置。
- 主要流程不依赖 hover、长按或拖拽；键盘焦点可见，屏幕阅读器能识别按钮与状态。
- 空库存、暂无生涯、加载中、存档错误、资源缺失、离线均有明确反馈与可行动出口。

### 玩法与恢复

- 新征程 → 开包 → 五人注册 → 备战 → 四场比赛 → 成长/补强 → 结算完整走通。
- 已有征程可以继续；打开详情、切换页面、刷新不会重新产生随机结果。
- 防止双击重复提交；存档 revision 冲突时要求重新载入，不静默覆盖。
- 第4场后不发即刻失效的成长；历史图鉴不混入本轮候选。
- 中断开包、回合间和成长选择后可恢复；模拟存储不可用/写入失败时不丢弃旧档。

### PWA 与性能

- Android 与 iOS 分别验证浏览器及安装启动，检查启动图标、安全区与返回。
- 首次联网完成缓存后断网重开，核心征程能继续；未缓存图像合理降级。
- 旧版存档在新版加载时兼容或明确提示，不自动清除；导入失败不覆盖当前存档。
- 更新过程中断网保留可启动版本，进行中的比赛不会被强制更新中断。
- 建立中端手机性能基线：目标交互反馈在约 200ms 内可见；开包和滚动采样检查掉帧，减少同时运行的粒子、模糊与大面积滤镜。这是待测目标，不是当前性能结论。
- 图片按尺寸加载、固定占位避免布局跳动；检查资源 404 和字体回退。
