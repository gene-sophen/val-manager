## 历史建议路线（2026-09-20）

玩家方向已确认：每次随机开包建队、肉鸽式随机与阶段成长、亲自指挥、联赛征程与队伍故事。用户希望避免长期卡库累积为毕业队伍；推荐每次征程重置实战阵容与成长，保留图鉴/荣誉/历史。完整流程见[《完整游玩流程与随机成长设计》](完整游玩流程与随机成长设计.md)，代码现状与审计见[《游戏内容与可玩版本工作计划》](游戏内容与可玩版本工作计划.md)。具体频率、持续范围与数值仍需形成可评审草案。

| 顺序 | 目标 | 交付标准 |
|---|---|---|
| 0 | 首版玩法规则 | 固定起始额度、征程长度、成长频率与继承/重置；赛事、失败和补强规则 |
| 1 | 抽卡阵容进入真实比赛 | 开包进本次库存、手选特工/IGL/战术、主界面接引擎、基本存档 |
| 2 | 连续比赛与随机成长 | 开局专长→比赛/指挥→复盘→成长三选一→下一场；效果真实生效 |
| 3 | 一个完整赛段 | 固定对手、完整赛程/排名/晋级、相应系列赛与地图、淘汰后继续 |
| 4 | 阶段大成长与征程结算 | 有限随机补强、重复卡处理、成长组合、图鉴/战绩保留、阵容与资源重置 |
| 5 | 试玩验证 | 检查不同起手与成长路线、成型节奏、指挥感和重玩意愿，再扩展完整赛年 |

现状校正：引擎已有 v3 报告、玩家教练窗口及交互观赛；UI v2 已有页面与视觉资产，但赛事数据和操作仍主要是示意。随机成长与征程状态是当前新增的 P0 缺口。先验证“开包—组队—比赛—成长—下一场”；大规模隐藏暗属性、日常活动、商业化和联网 PVP 后置。定向兑换不再列为必做。

## 三、开发阶段规划（已拍板：纯 Web）

**技术形态：纯 Web（H5）** —— 卡面与出卡特效已是 HTML/CSS/JS 实现，直接作为游戏前端技术栈，零迁移成本。

**开发节奏：全部设计完成后再开工**，设计阶段不写游戏代码。

### 开发顺序（设计全部定稿后）

1. **战斗模拟器（无 UI）**：Python/JS 脚本直接吃 `数据源/` 的 JSON，验证战斗数值（铜队 vs 钻队胜率、单局时长、偏科队收益）——已有管线先例 `sim_packs.py`
2. **前端可玩原型**：开包 → 收藏/组队 → 模拟比赛（文字战报）→ 结算，卡面与特效直接复用现有原型
3. **垂直切片**：串起最小核心循环（开包 → 组队 → 联赛 → 奖励 → 再开包）
4. **完整版**：观赛演出、地图 ban/pick、任务活动、存档

## 五、开发进度

- ✅ **推演引擎 v0**（`引擎/`，纯 JS 零依赖）：节点图地图、tick 回合推演、效用 AI、6 战术族、经济系统、批量模拟 CLI、平衡自检。实测 ~790 场/秒；金 vs 铜 82.6% 胜率（目标区间 65~85%）；攻防 49:51 平衡。报告见 `引擎/BALANCE_v0.md`
